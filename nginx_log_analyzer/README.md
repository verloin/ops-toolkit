# Nginx Log Analyzer — техническое задание

## 1. Имя файла

```text
nginx_log_analyzer.py
```

## 2. Назначение

Скрипт должен анализировать логи Nginx, находить HTTP-запросы с кодами ответа `5xx`, агрегировать найденные ошибки и сохранять результат в CSV-отчёт.

Основные задачи:

* анализировать Nginx `access.log`;
* находить HTTP status code в диапазоне `500–599`;
* извлекать IP-адрес клиента;
* извлекать дату и время запроса;
* извлекать URI;
* агрегировать ошибки по времени, IP, URI и HTTP status code;
* сохранять итоговый отчёт в формате CSV.

---

## 3. Запуск из командной строки

Скрипт должен принимать два обязательных аргумента:

1. путь к входному лог-файлу Nginx;
2. путь к результирующему CSV-файлу.

### Пример запуска

```bash
python nginx_log_analyzer.py /var/log/nginx/access.log report.csv
```

Исходный лог-файл должен открываться только для чтения и не должен изменяться скриптом.

---

## 4. Поддерживаемые логи

Основным источником данных должен быть Nginx `access.log`.

> `error.log` не следует использовать как основной источник HTTP status code, так как стандартный `error.log` Nginx обычно не содержит код HTTP-ответа для каждого запроса.

Скрипт должен поддерживать стандартный формат Nginx `combined` / `access_log`.
Пример строки:

```text
192.168.1.10 - - [23/Sep/2026:10:15:42 +0000] "GET /api/users?id=10 HTTP/1.1" 502 157 "-" "curl/8.0"
```

---

## 5. Логика обработки

Скрипт должен:

1. открыть входной файл для чтения;
2. читать файл построчно;
3. не загружать весь лог-файл целиком в память;
4. для каждой строки извлекать:
   * IP-адрес клиента;
   * дату и время;
   * HTTP-метод;
   * URI;
   * HTTP status code;
5. отбирать только записи с кодами:

```text
500–599
```

6. учитывать только успешно распознанные строки;
7. подсчитывать количество одинаковых ошибок.

---

## 6. Нормализация URI

При агрегации рекомендуется исключать query string.
Например:

```text
/api/users?id=10
/api/users?id=20
```

должны считаться одним URI:

```text
/api/users
```

Это позволит избежать разделения одинаковых endpoint'ов из-за разных GET-параметров.

---

## 7. Агрегация

Данные должны группироваться по комбинации:

```text
timestamp + ip + uri + status
```

Время необходимо агрегировать с точностью до одной минуты.
Например, несколько запросов:

```text
10:15:01  10.10.10.5  /api/login  502
10:15:17  10.10.10.5  /api/login  502
10:15:48  10.10.10.5  /api/login  502
```

должны быть объединены в одну запись:

```text
2026-09-23 10:15,10.10.10.5,/api/login,502,3
```

---

## 8. Формат CSV-отчёта

CSV-файл должен содержать заголовок.
Минимальный набор колонок:

```csv
timestamp,ip,uri,status,count
```

Пример:

```csv
timestamp,ip,uri,status,count
2026-09-23 10:15,10.10.10.5,/api/login,502,17
2026-09-23 10:16,10.10.10.8,/api/users,500,4
```

Результат рекомендуется сортировать:

1. по времени;
2. внутри одного временного интервала — по `count` в порядке убывания.

---

## 9. Обработка ошибок

Скрипт должен корректно обрабатывать следующие ситуации.

### Неверные аргументы

Если передано неверное количество аргументов, скрипт должен:

* вывести сообщение об ошибке;
* вывести пример правильного запуска;
* завершиться с ненулевым exit code.

Пример:

```text
Usage: python nginx_log_analyzer.py <input_log> <output_csv>
```

### Входной файл не существует
Если указанный лог-файл не найден, скрипт должен вывести понятное сообщение об ошибке и завершить работу.

### Вместо файла указана директория
Если путь указывает на директорию, скрипт должен завершиться с ошибкой.

### Недостаточно прав
Если файл невозможно прочитать из-за отсутствия прав, скрипт должен вывести соответствующее сообщение.

### Ошибка записи CSV
Если результирующий CSV-файл невозможно создать или записать, скрипт должен завершиться с ошибкой.

### Некорректная строка в логе
Одна повреждённая или неизвестная строка не должна останавливать обработку всего файла.
Такая строка должна быть пропущена.

---

## 10. Статистика выполнения

После завершения анализа скрипт должен вывести в `stdout` краткую статистику.
Например:

```text
Processed lines: 150000
5xx records found: 127
Invalid lines skipped: 3
Report written to: report.csv
```

Необходимо вывести:
* количество обработанных строк;
* количество найденных записей `5xx`;
* количество пропущенных некорректных строк;
* путь к созданному CSV-файлу.

---

## 11. Коды возврата

Скрипт должен использовать exit codes.

| Код    | Значение            |
| ------ | ------------------- |
| `0`    | Успешное завершение |
| `!= 0` | Ошибка выполнения   |

Ненулевой код должен использоваться при:

* неверных CLI-аргументах;
* отсутствии входного файла;
* ошибке чтения файла;
* ошибке создания или записи CSV;
* других критических ошибках.

---

## 12. Технические требования

Скрипт должен быть написан на:

```text
Python 3
```

Для базовой реализации рекомендуется использовать только стандартную библиотеку Python.
Код необходимо разделить на логические функции, например:

```text
parse_arguments()
parse_log_line()
aggregate_records()
write_csv()
main()
```

Дополнительные требования:

* не использовать глобальные переменные для хранения состояния программы;
* использовать `with` при работе с файлами;
* читать лог построчно;
* ошибки выводить в `stderr`;
* обычный результат и статистику выводить в `stdout`;
* код должен быть понятным и поддерживаемым;
* функции должны выполнять одну логическую задачу.

---

## 13. Требования к производительности

Скрипт должен корректно работать с большими лог-файлами.
Не допускается чтение всего `access.log` в память следующим способом:

```python
file.read()
```

или:

```python
file.readlines()
```

Основная обработка должна выполняться построчно.
Допускается хранение в памяти структуры с агрегированными результатами.

---

## 14. Критерии готовности

Задача считается выполненной, если:

* [ ] скрипт запускается из командной строки;
* [ ] корректно читает Nginx `access.log`;
* [ ] распознаёт HTTP status code `500–599`;
* [ ] записи `2xx`, `3xx` и `4xx` не попадают в отчёт;
* [ ] корректно извлекаются IP, URI и timestamp;
* [ ] query string исключается из URI при агрегации;
* [ ] время агрегируется с точностью до минуты;
* [ ] одинаковые события объединяются и получают поле `count`;
* [ ] результат сохраняется в CSV;
* [ ] CSV содержит заголовок;
* [ ] повреждённые строки не приводят к падению программы;
* [ ] ошибки файловой системы обрабатываются корректно;
* [ ] при успешной работе возвращается exit code `0`;
* [ ] при критической ошибке возвращается ненулевой exit code;
* [ ] пустой лог создаёт CSV только с заголовком;
* [ ] лог без `5xx` создаёт CSV только с заголовком.

---

## 15. Ожидаемый результат

После запуска:

```bash
python nginx_log_analyzer.py /var/log/nginx/access.log report.csv
```

должен быть создан файл:

```text
report.csv
```

с агрегированной статистикой HTTP-ошибок `5xx` вида:

```csv
timestamp,ip,uri,status,count
2026-09-23 10:15,10.10.10.5,/api/login,502,17
2026-09-23 10:16,10.10.10.8,/api/users,500,4
```

Цель задачи — отработать на практике типичные задачи DevOps/SRE-скриптинга на Python:

* CLI-интерфейс;
* обработку файлов;
* парсинг логов;
* работу с большими файлами;
* агрегацию данных;
* обработку исключений;
* exit codes;
* `stdout` / `stderr`;
* экспорт результатов в CSV.
